# OpenAPI для Yandex Tracker API v3

Официальной OpenAPI-спецификации у Трекера нет. `tracker.openapi.json` собран скриптом `build_openapi.py` из markdown-версий страниц [справочника API](https://yandex.ru/support/tracker/ru/api/about-api). Список страниц скрипт берёт из `llms.txt`.

## Пересборка

```bash
python3 crates/tracker-api/spec/build_openapi.py --cache /tmp/tracker-api-docs
```

- `--cache` — каталог для скачанных страниц;
- `--offline` — собрать из уже скачанных страниц, без сети;
- `--out` — куда записать результат (по умолчанию `tracker.openapi.json` рядом со скриптом).

В stderr скрипт печатает отчёт: сколько операций собрано, какие методы описаны на нескольких страницах и где тело запроса описано словами, а не таблицей.

Нужен только Python 3.10+, сторонних пакетов нет.

## Что внутри

- 195 операций на 130 путях, по одному тегу на раздел справочника.
- Параметры пути, запроса и тела берутся из таблиц «Ресурс», «Параметры запроса» и «Параметры тела запроса», с учётом разделов «Обязательные» и «Дополнительные» и вложенных объектов («Поля объекта `x`»).
- Схемы ответов строятся из таблиц «Параметры ответа» (блок под катом, заголовок «Параметры ответа» или блок «Параметры объекта …» во вкладке успешного ответа), примеры — из JSON-примеров справочника, если их удаётся разобрать.
- Заголовки ответов постраничной выдачи (`X-Total-Pages`, `X-Total-Count`, `Link`, `X-Scroll-Id`, `X-Scroll-Token`) описаны в `components.headers` и указаны у операций, где о них пишет справочник.
- Ошибки — общая схема `Error`: `errors`, `errorsData`, `errorMessages`, `statusCode`, `invocation-info`.
- Авторизация: `OAuth <токен>` или IAM-токен `Bearer`. Заголовки `X-Org-ID` и `X-Cloud-Org-ID` описаны общими параметрами; нужен один из них.
- `x-access-level` у каждой операции — уровень доступа для MCP-сервера:
  - `read` — `GET` и `POST`, которые только читают (`_search`, `_count`, `_list` и подобные);
  - `destructive` — `DELETE`, удаление тегов очереди и изменение прав доступа;
  - `write` — всё остальное.

## Постраничная выдача

- Обычная: параметры `page` и `perPage` (по умолчанию 50), в ответе `X-Total-Pages` и `X-Total-Count`.
- Относительная: параметры `perPage` и `id`, ссылка на следующую страницу — в заголовке `Link` (`rel="next"`). В поиске задач с телом `{"queue": …}` работает только она: `page` игнорируется и возвращается первая страница.
- Прокрутка в `POST /v3/issues/_search`: первый запрос с `scrollType` (`sorted` или `unsorted`), `perScroll` (до 1000) и необязательным `scrollTTLMillis`; следующие — с `scrollId` из заголовка `X-Scroll-Id` (или по ссылке из `Link`). С `keys` и `queue` прокрутка не работает: API отвечает 400 «Прокрутка результатов не поддерживается», вместо этого нужны `filter`, `query` или `query2`.
- `X-Scroll-Token` в поиске не нужен, но нужен, чтобы досрочно освободить прокрутку: `POST /v3/system/search/scroll/_clear` с телом `{"<X-Scroll-Id>": "<X-Scroll-Token>"}`.
- У части списков вместо заголовков счётчики в теле: `{"hits", "pages", "values"}` в поиске сущностей и отчётов, `{"users", "hasNext"}` и `{"events", "hasNext"}` в относительных списках пользователей и событий, `{"links"}` в связях задачи с пагинацией.

## Проверено на реальном API

Проверено запросами только на чтение (`GET` и читающие `POST`) и запросами к заведомо несуществующим объектам, на задачах и настройках тестовой очереди. Исправления сделаны исключениями в `build_openapi.py` (раздел «исключения»: `RESPONSE_SHAPES`, `RESPONSE_WRAPPERS`, `RESPONSE_FIELD_TYPES`, `BODY_REQUIRED`, `BODY_SCHEMAS`, `QUERY_PARAM_SCHEMAS`) и не теряются при пересборке.

Форма ответов:

- Совпадает со справочником: массивы — очереди, поиск и подсказки задач, комментарии, переходы, связи, история изменений, файлы, учёт времени, внешние связи, доски (`/v3/boards`, `/v3/boards/_paginate`), колонки, компоненты, версии очереди, поля очереди, триггеры, макросы, пользователи, приоритеты, резолюции, приложения, проекты старого API, поиск дашбордов, связи и комментарии сущностей; объекты — задача, очередь, поле, права пользователя на очередь, права и расширенные права сущности, поиск сущностей и отчётов, относительные списки пользователей и событий.
- Исправлено: `GET /v3/fields` и `GET /v3/queues/{queueId}/localFields` возвращают массив полей, а не объект.
- Исправлено: `GET /v3/issues/{issueId}/checklistItems` возвращает массив пунктов, а не один пункт.
- Исправлено: `POST /v3/issues/_count` возвращает число без обёртки.
- Исправлено: `GET /v3/queues/{queueId}/tags` — массив строк.
- Исправлено: `GET /v3/queues/{queueId}/workflows` — объект «идентификатор рабочего процесса → массив типов задач».
- Исправлено: `GET /v3/issues/{issueId}/comments/{commentId}` — объект комментария, `POST /v3/issues/{issueId}/links/_list` — объект с массивом `links` (раньше схемы не было: таблицы стоят не под катом).
- Исправлено: в поиске сущностей и отчётов поля сущности перенесены в элементы `values`, в относительном списке пользователей — в элементы `users`; справочник перечисляет их вперемешку с полями обёртки.

Поля и типы:

- Типы полей задачи, комментария, очереди, перехода, связи, записи истории, поля задачи, колонки, компонента, приоритета, резолюции, пользователя совпадают со схемами (целые числа описаны как `number`).
- Исправлено: `id` проекта старого API — строка, а не число.
- Добавлено: поле `screen` у переходов задачи — есть, если при переходе заполняются поля.
- Добавлено: в схеме ошибки поля `errorsData` и `invocation-info`, которых нет в справочнике.

Обязательные поля и параметры:

- `summary` и `queue` при создании задачи обязательны и по справочнику, и по описанию полей в `GET /v3/fields`.
- Исправлено: `comment` при выполнении перехода необязателен. Таблица справочника называет его обязательным, но текст той же страницы говорит, что поля передаются, только если это позволяют настройки перехода; в истории задач тестовой очереди есть переходы через API без комментария.
- Исправлено: при создании автодействия `filter` и `query` необязательны по отдельности — нужен хотя бы один (примечание на странице справочника).
- Исправлено разбором: подзаголовок «Поле объекта» (в единственном числе) — `id` доски при создании спринта больше не обязательное поле верхнего уровня, а поле объекта `board`; обязательные поля элементов `gaps` при создании отсутствий относятся к элементам массива.
- Исправлено: тело `POST /v3/system/search/scroll/_clear` — объект «X-Scroll-Id → X-Scroll-Token», а не поля `scrollId` и `scrollToken`: API проверяет подпись по ключам объекта (на чужой ключ отвечает 403 «Некорректная подпись»).
- Исправлено: в поиске задач `scrollId` и `id` — строки (справочник пишет «Число»), `perScroll` и `scrollTTLMillis` — целые числа, `scrollType` — `sorted` или `unsorted`; раньше все параметры прокрутки получали тип первого.

Пути:

- `GET /v2/filters/{filterId}` существует: на несуществующий фильтр API отвечает 404 «фильтр не существует», а не «Requested action … was not found», как на неизвестный путь. `DELETE` на несуществующий фильтр по пути v2 тоже отвечает 404 про фильтр, поэтому путь удаления оставлен из справочника — v2.
- `GET /v3/queues/{queueId}/autoactions/{autoactionId}/logs/{runId}` (в справочнике `QUEUE_ID/…/AUTOACTION_RUN_ID`) и `…/logs` существуют. `runId` — 24 шестнадцатеричных символа, другое значение API отклоняет с 400 «Incorrect data format»; это добавлено в описание параметра.
- `GET /v3/queues/{queueId}/triggers/{triggerId}/webhooks/log` существует (404 про несуществующий триггер).
- `GET /v3/boards/{boardId}/sprints` существует; для доски без спринтов API отвечает 400 «У доски этого типа не может быть спринтов».
- В API есть `GET /v3/queues/{queueId}/autoactions` (список автодействий), которого нет в справочнике; в спецификацию он не добавлен.

Уровни доступа:

- Пройдены все `POST`, `PATCH`, `PUT` и `DELETE`. Читающие `POST` (`_search`, `_count`, `links/_list`, освобождение прокрутки) — `read`; все `DELETE`, удаление тегов очереди и изменение прав доступа к очереди, дашборду и сущности — `destructive`. Изменений не понадобилось.

## Не проверено

Без изменяющих запросов проверить нельзя:

- Заголовки ответов (`X-Total-Pages`, `X-Total-Count`, `Link`, `X-Scroll-Id`, `X-Scroll-Token`): клиент, через который шла проверка, не показывает заголовки. Описаны по справочнику.
- Схемы ответов на создание, изменение и удаление (в том числе массив в ответе на создание версии очереди и на выполнение перехода — так в примерах справочника), коды `201`/`200`/`204`.
- Обязательность полей в телах запросов на запись, кроме перечисленных выше, и реальная обязательность `comment` на переходах с экраном.
- `DELETE /v3/filters/{filterId}`: работает ли удаление фильтра по пути v3.
- Объекты, которых нет в тестовой очереди: версии, компоненты и локальные поля очереди, пункты чеклиста, файлы, спринты, дашборды, виджеты, фильтры, макросы, триггеры, автодействия, рабочие процессы целиком, отсутствия.

## Ограничения

- Имена параметров пути приведены к единому виду (`{id_задачи}` → `{issueId}`), исходное имя из справочника — в `x-docs-name`.
- Где тип в справочнике описан словами («объект, число или строка»), строгого типа нет, исходное описание — в `description`.
- В схемах ответов только основные поля. У задач бывают ещё глобальные пользовательские поля и локальные поля очередей.
- Справочник иногда ошибается или расходится с реальным API. Проверенные расхождения исправлены (см. выше), остальные места спецификация повторяет за справочником.
