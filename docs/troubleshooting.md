# Решение проблем

Ошибки HTTP-режима (`401`, `400 missing_organization`, `403` по `Host` и `Origin` и другие) описаны в [HTTP-режиме](http.md#проблемы).

## Homebrew не ставит формулу из стороннего tap

Устанавливайте по полному имени, а tap добавляйте с полным адресом: он размещён на SourceCraft, а не на GitHub.

```bash
brew tap filipov-dev/tap https://git.sourcecraft.dev/filipov-dev/homebrew-tap.git
brew install filipov-dev/tap/tracker-mcp
```

## macOS: Keychain спрашивает разрешение

macOS может спросить, разрешить ли `tracker-mcp` доступ к записи `dev.filipov.tracker-mcp` в связке ключей, — обычно когда токен сохранила одна сборка бинарника, а читает другая. Нажмите «Всегда разрешать», иначе вопрос будет повторяться при каждом запуске сервера.

Бинарник из Homebrew и релизных архивов подписан Developer ID, поэтому после обновления разрешение, как правило, сохраняется. Бинарник, собранный из исходников, не подписан: после каждой пересборки macOS считает его новой программой и спрашивает снова.

Когда сервер запускает MCP-клиент, окно с вопросом появляется поверх других окон, а клиент ждёт ответа. Если клиент пишет, что сервер не запустился или не ответил, проверьте, нет ли такого окна.

## Linux: Secret Service недоступен

В Linux токен хранится через Secret Service (D-Bus); `libdbus-1` не нужна. Ошибка `no Secret Service (org.freedesktop.secrets) is available …` при `connect`, `auth` или `serve` означает одно из:

- в сессии не запущен провайдер Secret Service — GNOME Keyring, KeePassXC (с включённой интеграцией Secret Service), KWallet и т. п.;
- нет сессионной шины D-Bus: например, при входе по SSH на сервер без графической сессии;
- связка ключей заблокирована и разблокировать её некому.

Запасного файлового хранилища нет, и хранить токен в переменной окружения или файле нельзя — это намеренное ограничение. Варианты:

- запустить провайдер вручную ([Linux без Secret Service](cli.md#linux-без-secret-service): `dbus-run-session` и `gnome-keyring-daemon --unlock`);
- запустить `tracker-mcp` на рабочей машине с графической сессией;
- использовать [HTTP-режим](http.md): там хранилище не нужно, токен передаёт агент в заголовке запроса.

## Linux: ошибка проверки сертификата

Сертификат Tracker API проверяется по корневым сертификатам системы. Если запросы к API падают с ошибкой TLS или сертификата, проверьте, что они установлены: в минимальных образах (Debian/Ubuntu slim и т. п.) их нет: поставьте пакет `ca-certificates` или укажите файл сертификатов в переменной `SSL_CERT_FILE`.

## Работа по SSH

- `connect` и `auth login` по SSH не открывают браузер (как и в Linux без графической сессии и с `--no-browser`): ссылки на создание приложения и получение токена печатаются, откройте их на своём компьютере, а токен вставьте в терминал.
- В Linux по SSH обычно нет сессии D-Bus и Secret Service — см. [выше](#linux-secret-service-недоступен).
- В macOS по SSH связка ключей входа может быть заблокирована: разблокируйте её (`security unlock-keychain`) или выполните `connect` в обычном сеансе.
- В Windows Credential Manager есть только в сеансе, вошедшем с паролем: в SSH-сеансе со входом по ключу, в службе или задаче планировщика без сохранённого пароля `auth` и `serve` падают с ошибкой «A specified logon session does not exist». Выполните `connect` и запускайте MCP-клиент в обычном сеансе пользователя ([Windows](clients.md#windows)) или используйте [HTTP-режим](http.md).

## «no Tracker token is stored for profile …»

Для профиля из `serve --profile` нет токена в системном хранилище. Проверьте имя профиля в конфигурации клиента и сохраните токен:

```bash
tracker-mcp auth status --profile <профиль>
tracker-mcp auth login --profile <профиль>
```

Профиль по умолчанию для `serve` и `auth` — `default`, а `connect` по умолчанию создаёт профиль с именем клиента (`claude-code`, `codex`). `tracker-mcp serve --status --profile <профиль>` покажет, чего не хватает для запуска: токена или организации.

## Tracker отклонил токен: HTTP 401

`connect`, `auth login` или `auth status` пишут `Tracker rejected the token (HTTP 401)`, либо инструмент возвращает ошибку с кодом `401`. Токен скопирован не полностью, истёк или отозван. Получите новый по ссылке приложения ([получение токена](oauth.md#получение-токена)) и замените сохранённый:

```bash
tracker-mcp auth login --profile <профиль>
```

Сервер читает токен из хранилища при запуске, поэтому после замены перезапустите его: переподключите сервер в клиенте (`/mcp` в Claude Code) или перезапустите клиент.

## IAM: yc не выдаёт токен

У профиля с IAM ([IAM-токены](iam.md)) `auth login`, `auth status` или инструмент пишут об ошибке `yc`:

- **the Yandex Cloud CLI `yc` was not found** — `yc` не установлен или не виден в `PATH` процесса. MCP-клиент запускает сервер со своим `PATH`, который может отличаться от `PATH` терминала: укажите абсолютный путь, `tracker-mcp auth login --profile <профиль> --auth iam --yc-path <путь к yc>` (`command -v yc` покажет путь).
- **`yc iam create-token … failed`** — `yc` не настроен или сессия истекла. Выполните показанную в ошибке команду в терминале: для федеративного аккаунта она откроет браузер для входа, для сервисного — проверит ключ профиля `yc`. Подробности `yc` в ошибке обрезаны, а похожие на секреты значения заменены на `***`: смотрите полный вывод, запустив команду сами.
- **`did not finish in … s`** — `yc` ждёт входа в браузере или не может достучаться до Yandex Cloud. Сначала выполните `yc iam create-token` в терминале, чтобы `yc` сохранил сессию.
- **`profile … uses IAM tokens, which work only with a Yandex Cloud organization`** — у профиля организация Yandex 360. IAM-токены работают только с организацией Yandex Cloud: `tracker-mcp auth login --profile <профиль> --auth iam --cloud-org-id <ID>`.

`Tracker rejected the IAM token (HTTP 401)` или `401` у инструмента после повтора с новым токеном означает, что Tracker не принимает пользователя `yc`: проверьте, что `yc` вошёл в нужный аккаунт (`yc config list`, `--yc-profile`), аккаунт состоит в этой организации Yandex Cloud и у него есть доступ к Tracker (сервисный аккаунт подключают через поддержку Tracker). Перезапускать сервер после исправления не нужно: следующий запрос получит новый токен.

## Нет доступа: HTTP 403

`Tracker denied access (HTTP 403)` при проверке токена или ошибка `403` у инструмента:

- **Неверная организация.** ID или тип организации не совпадает с той, к которой у пользователя есть доступ: Yandex 360 для бизнеса — `X-Org-ID`, Yandex Cloud Organization — `X-Cloud-Org-ID`. ID показан в Tracker на странице «Администрирование → Организации». Исправьте: `tracker-mcp auth login --profile <профиль> --org-id <ID>` (или `--cloud-org-id <ID>`).
- **Нет прав у пользователя.** Пользователь токена не видит очередь или задачу либо не может менять её. Права выдаёт администратор очереди в Tracker.
- **Нет прав у токена.** Запись токеном приложения только с `tracker:read`. Добавьте приложению `tracker:write` и получите новый токен ([права приложения](oauth.md#права-приложения)).

## Агенту не хватает инструмента

- Инструмент записи или удаления не зарегистрирован: сервер работает только на чтение. Вызов по имени возвращает ошибку с нужным флагом. Перезапустите сервер с `--allow-write` или `--allow-destructive`, например повторным `connect … --allow-write`.
- Инструмент из выключенного набора: агент найдёт его через `api_search`, в ответе сказано, каким `--toolsets` его включить. Вызвать операцию в пределах уровня доступа можно и через `api_request`.
- Инструментов загрузки файлов нет в HTTP-режиме: там локальные файлы выключены.

## Клиент не видит сервер или его инструменты

- Перезапустите клиент после `connect` или правки конфигурации.
- Укажите в конфигурации клиента абсолютный путь к бинарнику (`command -v tracker-mcp`).
- Запустите команду из конфигурации вручную, например `tracker-mcp serve --profile codex`. Ошибки запуска (нет токена, нет организации, неизвестный набор, несуществующий каталог в `--allow-path`) печатаются в stderr. Если ошибок нет, сервер ждёт сообщений MCP на stdin — остановите его `Ctrl-C`.
- Для подробных логов добавьте в аргументы сервера `--log-level debug`. Логи пишутся в stderr.

## Файл «is outside the allowed directories»

Инструменты работают с локальными файлами только в рабочем каталоге сервера, системном временном каталоге и каталогах из `--allow-path`. Если клиент запускает сервер в домашнем каталоге или в `/`, рабочий каталог не разрешён. Добавьте нужный каталог в аргументы сервера: `--allow-path /path/to/project` ([Безопасность](security.md#локальные-файлы)).

## Ответ слишком большой

Ответ API больше `--max-response-bytes` (256 КиБ по умолчанию) возвращается ошибкой с подсказкой сузить запрос. Запросите только нужные поля (`fields` в `get_issue` и `search_issues`), уменьшите `perPage`, уточните фильтр или используйте [прокрутку](tools.md#постраничная-выдача). Лимит можно увеличить флагом `--max-response-bytes` в аргументах сервера.

## Запрос «Incorrect data format» или 400

Tracker отклонил аргументы. Проверьте схему инструмента (`api_search` с `tool_name`) и страницу справочника по ссылке в описании инструмента: тело запроса передаётся в `body`, `expand` и `fields` — строки через запятую.
