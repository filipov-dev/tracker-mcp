# Справочник CLI

```text
tracker-mcp <команда> [флаги]
```

| Команда | Назначение |
| --- | --- |
| [`connect`](#connect) | Подключить сервер к Claude Code или Codex одной командой. |
| [`serve`](#serve) | Запустить MCP-сервер через stdio или по HTTP ([`--http`](#serve---http)). |
| [`auth`](#auth) | Управлять токенами и организациями профилей: `login`, `status`, `logout`. |
| [`tools`](#tools) | Показать и проверить пользовательские инструменты из `tools.toml`: `list`, `check`. |
| [`call`](#call) | Вызвать инструмент сервера из консоли с правами профиля. |
| [`ui`](#ui) | Интерактивный просмотр профилей: настройки, права и их одобрение, регистрации в клиентах, пользователь токена, инструменты. |

`tracker-mcp --version` печатает версию, `tracker-mcp <команда> --help` — справку по команде.

## Профили

Профиль — имя, под которым хранятся токен и настройки одного клиента. Профиль по умолчанию — `default`, другой выбирается флагом `--profile`.

- **Токен** — только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Сервис `dev.filipov.tracker-mcp`, учётная запись — имя профиля. Из переменных окружения и `.env` токен не читается, в `profiles.toml` не пишется и не печатается ни одной командой. У профиля с IAM (`auth = "iam"`, федеративные и сервисные аккаунты) токена в хранилище нет: сервер получает его командой `yc iam create-token` и держит только в памяти ([IAM-токены](iam.md)).
- **Настройки** (без токена) — в `~/.config/tracker-mcp/profiles.toml`; в Linux учитывается `XDG_CONFIG_HOME`, в Windows файл лежит в `%APPDATA%\tracker-mcp\profiles.toml`. Файл создают `connect` и `auth login`:

  ```toml
  [profiles.default]
  client = "codex"           # клиент, в котором профиль зарегистрирован через connect
  client_id = "<ClientID>"   # OAuth-приложение пользователя, необязательно
  allow_write = false
  allow_destructive = false
  allow_path = ["/Users/me/work"]   # необязательно: каталоги для локальных файлов
  toolsets = []

  [profiles.default.org]
  type = "yandex360"         # или "cloud"
  id = "<ID организации>"
  ```

  Профиль с IAM-токенами дополнительно содержит `auth = "iam"` и необязательные `yc_profile` (профиль `yc`) и `yc_path` (абсолютный путь к `yc`); организация у него только `cloud`. Без `auth` профиль работает с OAuth-токеном.

Организация обязательна: Tracker принимает запросы только с её ID. Тип определяет заголовок:

| `type` | Организация | Заголовок |
| --- | --- | --- |
| `yandex360` | Yandex 360 для бизнеса | `X-Org-ID` |
| `cloud` | Yandex Cloud Organization | `X-Cloud-Org-ID` |

ID организации показан в Tracker на странице «Администрирование → Организации».

`allow_destructive = true` подразумевает запись: при сохранении профиля `allow_write` выставляется тоже.

Права профиля (`allow_write`, `allow_destructive`, `allow_path`) — граница доступа stdio-сервера: `serve`, `call` и `ui` не дают больше. Меняет их `tracker-mcp ui` (или `connect --allow-write`/`--allow-destructive`, или правка файла). На macOS права сверх чтения действуют только после одобрения владельцем: одобренная копия прав хранится в Keychain (сервис `tracker-mcp.access`, учётная запись — имя профиля), а `ui` и `connect` при повышении прав спрашивают Touch ID или пароль пользователя macOS. Понижение прав одобрения не требует. Если права в профиле шире одобренных, действует пересечение; если одобрения нет или Keychain недоступен — только чтение, сервер предупреждает в stderr. В Linux и Windows одобрения нет: права ограничивают разрешения токена и роли пользователя в Tracker ([Безопасность](security.md#уровни-доступа)). В HTTP-режиме профилей нет, права задают флаги `serve --http`.

Имя профиля: 1–64 символа из `A-Z`, `a-z`, `0-9`, `.`, `_`, `-`, не начинается с `-`.

### Linux без Secret Service

Запасного файлового хранилища нет. Если в сессии нет демона Secret Service (`org.freedesktop.secrets` на сессионной шине D-Bus), команды `auth` завершаются ошибкой с подсказкой. Запустите демон хранилища: GNOME Keyring, KDE Wallet или KeePassXC с интеграцией Secret Service. На машине без графической сессии можно поднять шину и разблокированное хранилище вручную:

```bash
dbus-run-session -- sh
# внутри новой оболочки; пароль хранилища читается из stdin
gnome-keyring-daemon --unlock --components=secrets
```

## connect

```text
tracker-mcp connect <claude-code|codex> [флаги]
```

Подключает сервер к MCP-клиенту: создаёт или обновляет профиль, получает и сохраняет токен и после подтверждения добавляет сервер в конфигурацию клиента. Токен не проходит через агента и не попадает в конфигурацию клиента: туда записывается только команда

```text
<путь к tracker-mcp> serve --profile <профиль> [--toolsets <a,b>] [--dynamic-toolsets]
```

Флагов доступа в конфигурации клиента нет: `serve` берёт права из профиля. Повторный `connect` переписывает регистрацию старых версий, в которой были флаги доступа, на команду без них.

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--profile <имя>` | имя клиента (`claude-code`, `codex`) | Профиль. |
| `--name <имя>` | `tracker` | Имя сервера в конфигурации клиента: 1–64 символа из `A-Z`, `a-z`, `0-9`, `_`, `-`. |
| `--scope <user\|project>` | `user` | `user` — для всех проектов пользователя; `project` — в `.mcp.json` текущего каталога (только Claude Code). |
| `--allow-write` | права профиля не меняются | Поставить профилю уровень записи. На macOS повышение прав спрашивает Touch ID или пароль; при отказе профиль сохраняет прежние права, а токен и регистрация всё равно сохраняются. |
| `--allow-destructive` | права профиля не меняются | Поставить профилю уровень удаления (включает запись; в профиль сохраняются оба флага). |
| `--toolsets <a,b,…>` | набор `serve` по умолчанию | Наборы инструментов; неизвестный набор — ошибка. |
| `--dynamic-toolsets` | выкл. | [Динамические наборы](tools.md#динамические-наборы): при запуске только поиск, запросы и управление наборами, остальное агент включает сам. Нужен клиент, который перечитывает список инструментов по уведомлению. |
| `--client-id <ID>` | из профиля | `ClientID` вашего OAuth-приложения (32 шестнадцатеричных символа). |
| `--org-id <ID>` | из профиля | ID организации Yandex 360 для бизнеса (`X-Org-ID`). |
| `--cloud-org-id <ID>` | из профиля | ID организации Yandex Cloud (`X-Cloud-Org-ID`). |
| `-y`, `--yes` | выкл. | Не задавать вопросов «да/нет»: оставить рабочий сохранённый токен и записать конфигурацию клиента. |
| `--skip-check` | выкл. | Сохранить токен без проверки запросом к API. |
| `--no-browser` | выкл. | Не открывать ссылки в браузере, только напечатать их. |
| `--iam` | выкл. (профиль с IAM остаётся на IAM) | IAM-токены от `yc` вместо OAuth-токена: для федеративных и сервисных аккаунтов. Нужна организация Yandex Cloud (`--cloud-org-id`); с `--client-id` и `--org-id` несовместим. |
| `--yc-path <путь>` | `yc` из `PATH` | IAM: абсолютный путь к `yc`. Сохраняется в профиль. |
| `--yc-profile <имя>` | активный профиль `yc` | IAM: профиль `yc` (`yc --profile`). Сохраняется в профиль. |

С `--iam` шагов 1 и 3 нет: OAuth-приложение и токен не нужны. Вместо них `connect` спрашивает (если не передан `--cloud-org-id` и его нет в профиле) только ID организации Yandex Cloud, получает токен через `yc` и проверяет его запросом `GET /v3/myself`, как [`auth login --auth iam`](#auth-login). Остальные шаги те же; в конфигурацию клиента записывается та же команда `serve --profile <профиль> …` ([IAM-токены](iam.md)).

Шаги:

1. **OAuth-приложение.** Своего приложения в `tracker-mcp` нет: токен выдаёт ваше собственное приложение Яндекс OAuth. Если в профиле ещё нет `client_id` (и не передан `--client-id`), `connect` открывает страницу создания приложения <https://oauth.yandex.ru/client/new/> и подсказывает настройки:
   - тип — «Для доступа к API или отладки»;
   - название — любое, например `tracker-mcp-<профиль>`, и контактная почта;
   - права — «Чтение из трекера» (`tracker:read`), а для `--allow-write` и `--allow-destructive` также «Запись в трекер» (`tracker:write`);
   - Redirect URI, если форма его спрашивает (платформа «Веб-сервисы»), — `https://oauth.yandex.ru/verification_code`.

   Затем спрашивает `ClientID` со страницы приложения, проверяет формат и сразу сохраняет его в профиль: повторный `connect` его больше не спрашивает. `ClientID` не секретный; Client secret не нужен. Если запись включается для профиля, приложение которого создано только с `tracker:read`, добавьте приложению право `tracker:write` и получите новый токен. Почему права лучше давать минимальные и по приложению на агента — в [OAuth-приложении и токене](oauth.md).
2. **Организация** — как в [`auth login`](#auth-login): флаг, профиль или вопрос о типе и ID.
3. **Токен.** Если в хранилище уже есть токен профиля и он проходит проверку, `connect` предлагает его оставить (с `--yes` — оставляет). Иначе открывает ссылку авторизации приложения `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`: войдите в аккаунт, от имени которого будет работать агент, разрешите доступ и вставьте показанный токен в скрытый ввод. Токен проверяется запросом `GET /v3/myself` и сохраняется в системное хранилище; если проверка не прошла, ничего не сохраняется.
4. **Профиль.** В `profiles.toml` записываются клиент, `client_id`, организация, наборы инструментов и `dynamic_toolsets` из флагов `connect` (наборы и `dynamic_toolsets` перезаписываются при каждом запуске), а с `--allow-write` или `--allow-destructive` — и уровень доступа. Без этих флагов права профиля не меняются (у нового профиля — только чтение).
5. **Конфигурация клиента.** `connect` показывает, что именно будет записано, и спрашивает подтверждение; при отказе (или без ответа) конфигурация не меняется, а токен и профиль остаются.
   - **Claude Code** — через его CLI: `claude mcp add --scope <scope> <имя> -- <путь> serve --profile <профиль> …`. Файлы Claude Code напрямую не правятся. Если сервер с таким именем уже есть и запускает `tracker-mcp`, он заменяется (`claude mcp remove` и снова `add`) после подтверждения.
   - **Codex** — таблица `[mcp_servers.<имя>]` в `$CODEX_HOME/config.toml` (по умолчанию `~/.codex/config.toml`):

     ```toml
     [mcp_servers.tracker]
     command = "/opt/homebrew/bin/tracker-mcp"
     args = ["serve", "--profile", "codex"]
     ```

     Остальные записи, комментарии и форматирование файла сохраняются; запись с тем же именем заменяется на месте.

   Запись с тем же именем, которая запускает другой сервер, а не `tracker-mcp`, заменяется только после явного ответа в терминале; с `--yes` `connect` завершается ошибкой и ничего не меняет. Чтобы подключить сервер рядом с ней, выберите другое имя через `--name`.

После подключения перезапустите клиент. В конфигурацию записывается абсолютный путь к запущенному бинарнику без раскрытия symlink: при установке через Homebrew путь `bin/tracker-mcp` переживает обновления.

Ссылки открываются в браузере по умолчанию. Браузер не открывается с `--no-browser`, по SSH (`SSH_CONNECTION`, `SSH_TTY`) и в Linux без графической сессии (`DISPLAY`, `WAYLAND_DISPLAY`); ссылки печатаются всегда, их можно открыть на своём компьютере.

Для каждого клиента используйте отдельный профиль и отдельное OAuth-приложение, чтобы токен каждого можно было отозвать независимо.

## serve

```text
tracker-mcp serve [--profile <имя>] [--allow-write] [--allow-destructive]
                  [--toolsets <набор,...>|all] [--dynamic-toolsets]
                  [--tools-file <путь>]... [--allow-path <каталог>]...
                  [--timeout <секунды>] [--max-response-bytes <байты>]
                  [--log-level <уровень>] [--status]
```

Запускает MCP-сервер через stdio: MCP-клиент (Claude Code, Codex и другие) запускает команду сам и общается с ней через stdin и stdout. HTTP-режим описан ниже, в [`serve --http`](#serve---http). Каждая операция Tracker API из встроенной спецификации — отдельный инструмент; имя инструмента — `operationId` операции в snake_case (`get_issue`, `search_issues`, `create_issue`). Кроме них всегда доступны `api_search` (поиск по всем операциям) и `api_request` (запрос к любому пути API в пределах уровня доступа), см. [MCP-инструменты](tools.md#api_search-и-api_request).

Токен и организация берутся только из профиля (`--profile`, по умолчанию `default`): токен — из системного хранилища, организация — из `profiles.toml`. Если чего-то нет, сервер не запускается и подсказывает команду `auth login`. В аргументах инструментов токена нет.

Профиль с IAM (`auth = "iam"`) хранилище не читает: сервер получает IAM-токен командой `yc iam create-token` перед первым запросом, заменяет его не реже раза в час и до истечения срока, держит только в памяти, а после ответа `401` один раз повторяет запрос с новым токеном ([как сервер обновляет токен](iam.md#как-сервер-обновляет-токен)).

| Флаг | Назначение |
| --- | --- |
| `--profile <имя>` | Профиль с токеном и организацией. |
| `--allow-write` | Сузить права профиля до записи (профиль должен разрешать запись). |
| `--allow-destructive` | Сузить права до удаления (профиль должен разрешать удаление); включает запись. |
| `--toolsets <набор,...>` | Наборы инструментов через запятую или `all`. С `--dynamic-toolsets` — наборы, включённые при запуске. |
| `--dynamic-toolsets` | [Динамические наборы](tools.md#динамические-наборы): при запуске только `api_search`, `api_request`, `list_toolsets`, `enable_toolset`, `disable_toolset` и пользовательские инструменты; наборы агент включает сам. Не сочетается с `--http`. |
| `--tools-file <путь>` | Дополнительный файл [пользовательских инструментов](tools.md#пользовательские-инструменты) в формате `tools.toml`; флаг повторяется. В HTTP-режиме читаются только эти файлы. |
| `--allow-path <каталог>` | Оставить из каталогов `allow_path` профиля только этот (он должен лежать внутри каталога профиля); флаг повторяется. |
| `--timeout <секунды>` | Таймаут одного запроса к API, по умолчанию 60. |
| `--max-response-bytes <байты>` | Предел ответа API, который возвращается агенту, по умолчанию 262144 (256 КиБ). Больший ответ — ошибка с подсказкой сузить запрос. С [фильтром `jq`](tools.md#фильтр-ответа-jq) предел относится к результату фильтра. |
| `--log-level <уровень>` | Уровень или фильтр логов в stderr (`info`, `debug`, `tracker_mcp_core=debug`). Без флага — переменная `RUST_LOG`, без неё — `warn`. |
| `--status` | Показать действующие настройки и выйти, не запуская сервер. |

### Уровни доступа и наборы

Права — из профиля ([Профили](#профили)): уровень доступа (`allow_write`, `allow_destructive`) и каталоги `allow_path`; без них — только чтение. Флаги `--allow-write`, `--allow-destructive` и `--allow-path` права только сужают: флаг, который просит больше, чем разрешено в профиле, — ошибка запуска с подсказкой. На macOS права сверх одобренных отсекаются с предупреждением в stderr, сервер при этом запускается; так регистрации старых версий с флагами доступа продолжают работать. Инструменты выше уровня не регистрируются вовсе; вызов такого инструмента объясняет, как поднять уровень.

Наборы по умолчанию — `issues`, `queues`, `boards` и `users`. `--toolsets` важнее настройки профиля `toolsets`, `--dynamic-toolsets` включает динамические наборы, без него действует `dynamic_toolsets` профиля. Неизвестный набор — ошибка запуска со списком допустимых.

Локальные файлы: рабочий каталог сервера (если это не корень файловой системы и не домашний каталог), системный временный каталог и каталоги `allow_path` профиля ([Локальные файлы](security.md#локальные-файлы)).

Пользовательские инструменты читаются при запуске из `tools.toml` рядом с `profiles.toml`, если файл есть, и из файлов `--tools-file`. Ошибка в файле — ошибка запуска; проверить файлы заранее можно командой [`tools check`](#tools).

Что входит в уровни и наборы, как устроены аргументы и ответы инструментов, `api_search` и `api_request` — в [MCP-инструментах](tools.md). Вырезание учётных данных из ответов и правила для локальных файлов — в [Безопасности](security.md).

### serve --status

```text
tracker-mcp serve --status [--profile <имя>] [--allow-write] [--allow-destructive] [--toolsets ...]
                  [--dynamic-toolsets] [--tools-file <путь>]...
```

Печатает, с какими настройками запустился бы сервер с теми же флагами: профиль, тип авторизации (`OAuth` или `IAM` с командой `yc`), сохранён ли токен (без значения; для IAM — что токен не хранится), организацию, уровень доступа и откуда он взят (флаги, профиль или по умолчанию), состояние одобрения (`Approval`; на macOS при урезанных правах — ещё строка `Warning`), наборы, включены ли динамические наборы, число инструментов, сколько пользовательских инструментов определено и зарегистрировано (и путь к `tools.toml`), разрешённые каталоги и путь к `profiles.toml`. Сервер не запускается, к API запросов нет. `--allow-destructive` без `--allow-write` показывается как `destructive (read, write and delete tools)`; флаг сверх прав профиля — та же ошибка, что у `serve`.

### serve --http

```text
tracker-mcp serve --http [--listen <IP:порт>] [--allowed-host <имя>]... [--allowed-origin <origin>]...
                  [--org-id <ID> | --cloud-org-id <ID>] [--max-request-bytes <байты>]
                  [--allow-write] [--allow-destructive] [--toolsets <набор,...>|all]
                  [--tools-file <путь>]... [--timeout <секунды>] [--max-response-bytes <байты>]
                  [--log-level <уровень>]
```

Запускает тот же сервер как HTTP-сервис (Streamable HTTP без сессий): `POST /mcp` и `GET /health`, по умолчанию на `127.0.0.1:8766`. Профилей и системного хранилища в этом режиме нет: каждый запрос агента несёт токен в `Authorization: OAuth <токен>` (или `Bearer <IAM-токен>`) и организацию в `X-Org-ID` или `X-Cloud-Org-ID`, если её не задаёт флаг сервера. Уровень доступа, наборы и пользовательские инструменты (`--tools-file`) задаются только флагами, локальные файлы выключены; `--profile`, `--allow-path`, `--status` и `--dynamic-toolsets` вместе с `--http` — ошибка. Права профиля и одобрение на macOS здесь не действуют: сервер не читает ни профилей, ни хранилища, токен присылает сам агент, и права ограничивает этот токен ([HTTP-режим](http.md#права-доступа)).

| Флаг | Назначение |
| --- | --- |
| `--http` | Режим HTTP вместо stdio. |
| `--listen <IP:порт>` | Адрес и порт, по умолчанию `127.0.0.1:8766`. |
| `--allowed-host <имя>` | Дополнительное допустимое значение `Host` (`имя` или `имя:порт`); флаг повторяется. |
| `--allowed-origin <origin>` | Допустимый `Origin` браузерного клиента; флаг повторяется. |
| `--org-id <ID>` | Организация Yandex 360 для всех запросов; другая организация в запросе отклоняется. |
| `--cloud-org-id <ID>` | Организация Yandex Cloud для всех запросов; другая организация в запросе отклоняется. |
| `--max-request-bytes <байты>` | Предел тела запроса MCP, по умолчанию 1048576 (1 МиБ). |

Коды ответов, Docker-образ, `compose.yaml` и подключение клиентов — в [HTTP-режиме](http.md).

## call

Вызывает инструмент сервера из консоли.

```text
tracker-mcp call [--profile <имя>] [--allow-write] [--allow-destructive]
    [--allow-path <каталог>]... [--toolsets <набор,...>] [--tools-file <путь>]...
    [--timeout <секунды>] [--max-response-bytes <байты>]
    [<инструмент> [<имя>=<значение> | <имя>:=<JSON>]... [--args <JSON>|-] [--schema] [--yes] [--raw]]
```

- Без инструмента печатает инструменты, доступные профилю, с уровнем доступа и первой строкой описания. `--schema` печатает схему аргументов инструмента.
- Сервер собирается как в `serve` через stdio без флагов: права профиля (на macOS — одобренные), флаги только сужают. По умолчанию включены все наборы (`--toolsets` сужает), наборов по запросу нет. Клиент MCP работает в этом же процессе, поэтому проверка аргументов, уровни доступа, фильтр `jq` и вырезание учётных данных те же, что у агента.
- Аргументы: `имя=значение` — тип берётся из схемы инструмента (числа, логические значения, JSON-массивы и объекты; для массива строк — список через запятую), `имя:=JSON` — всегда JSON, `--args` — все аргументы одним JSON-объектом (`-` — из stdin). Флаги команды пишутся до имени инструмента.
- Инструменты уровня удаления спрашивают подтверждение в терминале; `--yes` — без вопроса, без терминала вызов отклоняется.
- Результат: текстовые блоки (JSON — с отступами); `--raw` — ответ MCP целиком. Код выхода — 0, если инструмент выполнился, и 1, если он вернул ошибку (`isError`) или вызов не удался.

```bash
tracker-mcp call get_issue issueId=TEST-1 jq='{key, summary, status: .status.key}'
tracker-mcp call search_issues --args '{"body": {"query": "Assignee: me() Resolution: empty()"}}' perPage=5
tracker-mcp call api_request method=GET path=/v3/myself
```

## ui

Интерактивный просмотр профилей в терминале.

```text
tracker-mcp ui
```

Вкладки:

- **Profile** — настройки профиля и состояние токена: тип авторизации (OAuth или IAM с командой `yc`), есть ли токен в хранилище (сам токен не показывается), организация, `ClientID` OAuth-приложения, наборы.
- **Access** — права профиля и их одобрение. `r`, `w`, `d` — уровень, `a` — добавить каталог, `x` — убрать, `u` — отменить, `s` — сохранить. На macOS сохранение прав шире одобренных спрашивает Touch ID или пароль пользователя macOS.
- **Clients** — регистрации сервера в Claude Code (`~/.claude.json`, `.mcp.json` текущего каталога) и Codex (`$CODEX_HOME/config.toml`): профиль, флаги и расхождения с правами профиля. `f` регистрирует запись заново без флагов доступа (остальные аргументы `serve` сохраняются). Значения переменных окружения записей не читаются.
- **Account** — проверка токена (`c`): тип авторизации, организация и пользователь, от имени которого работает токен (`GET /v3/myself`). Разрешения OAuth-токена Tracker серверу не сообщает: их видно в приложении на oauth.yandex.ru (`tracker:read`, `tracker:write`) и в ролях пользователя в Tracker.
- **Tools** — инструменты, которые профиль даёт агенту (`c` — загрузить), `Enter` — вызвать с аргументами `имя=значение`, `?` — схема.

`q` или `Esc` — выход, `Tab` и `1`–`5` — вкладки, `F5` — перечитать. Без терминала (агент, CI) команда завершается ошибкой. HTTP-режим профилей не использует и здесь не показывается.

## auth

### auth login

```text
tracker-mcp auth login [--profile <имя>] [--org-id <ID> | --cloud-org-id <ID>] [--token-stdin] [--skip-check]
tracker-mcp auth login [--profile <имя>] --auth iam [--cloud-org-id <ID>] [--yc-profile <имя>] [--yc-path <путь>] [--skip-check]
```

| Флаг | Назначение |
| --- | --- |
| `--auth <oauth\|iam>` | Тип авторизации. Без флага — тип из профиля, для нового профиля — `oauth`. `--iam` — то же, что `--auth iam`. |
| `--yc-path <путь>` | IAM: абсолютный путь к `yc`; без него `yc` ищется в `PATH`. |
| `--yc-profile <имя>` | IAM: профиль `yc` (`yc --profile`); без него — активный профиль `yc`. |

Сохраняет OAuth-токен Tracker и организацию профиля:

1. Организация: `--org-id` (Yandex 360) или `--cloud-org-id` (Yandex Cloud); без флагов берётся из профиля, а если её там нет — спрашивается тип и ID.
2. Токен: скрытым вводом в терминале или, с `--token-stdin`, из stdin (например, из менеджера паролей). С `--token-stdin` организация не спрашивается: передайте флаг, если в профиле её ещё нет.
3. Проверка: запрос `GET /v3/myself` с токеном и заголовком организации; печатается логин пользователя. `--skip-check` пропускает проверку (без сети).
4. Токен сохраняется в системное хранилище (заменяя прежний), организация — в `profiles.toml`. Остальные настройки профиля не меняются; новый профиль создаётся с доступом только на чтение.

Токен выдаёт ваше собственное OAuth-приложение Yandex с доступом к Tracker. Если в профиле есть `client_id`, команда печатает ссылку для получения токена; создать приложение и сохранить `client_id` помогает [`connect`](#connect).

С `--auth iam` (федеративные и сервисные аккаунты, [IAM-токены](iam.md)) токен не вводится и не сохраняется:

1. Организация — только Yandex Cloud: `--cloud-org-id`, иначе из профиля, иначе спрашивается ID. `--org-id` и организация Yandex 360 в профиле — ошибка.
2. Проверка: токен получается командой `yc iam create-token [--profile <имя>]` (до трёх минут: для федеративного аккаунта `yc` может открыть браузер) и проверяется запросом `GET /v3/myself` с `Authorization: Bearer`; печатается логин. `--skip-check` не запускает `yc` и не обращается к API. `--token-stdin` с IAM — ошибка.
3. В `profiles.toml` записываются `auth = "iam"`, организация, `yc_profile` и `yc_path`. Если в хранилище остался OAuth-токен профиля, команда напоминает, что его можно удалить `auth logout`.

`auth login --auth oauth` переводит профиль с IAM обратно на OAuth и убирает из него настройки `yc`.

### auth status

```text
tracker-mcp auth status [--profile <имя>] [--skip-check]
```

Показывает профиль, тип авторизации (`Auth`), сохранён ли токен (без значения), организацию, пользователя, которому принадлежит токен (запрос `GET /v3/myself`; `--skip-check` — без запроса), `client_id`, клиент, в котором профиль зарегистрирован через `connect`, разрешены ли запись и удаление, наборы инструментов и путь к `profiles.toml`. Если проверка не прошла, причина печатается в строке `User`. Для профиля с IAM строка `Auth` показывает команду `yc`, хранилище не читается, а проверка получает токен через `yc` (с `--skip-check` `yc` не запускается).

### auth logout

```text
tracker-mcp auth logout [--profile <имя>] [--forget]
```

Удаляет токен профиля из системного хранилища. С `--forget` также удаляет настройки профиля из `profiles.toml`. Если токен больше нигде не нужен, отзовите его в настройках Яндекс ID. У профиля с IAM токена в хранилище нет: команда сообщает об этом, а недоступное хранилище для него не ошибка.

## tools

```text
tracker-mcp tools list [--tools-file <путь>]...
tracker-mcp tools check [--tools-file <путь>]...
```

Работают с [пользовательскими инструментами](tools.md#пользовательские-инструменты). Файл пользователя `tools.toml` рядом с `profiles.toml` читается всегда, если он есть; `--tools-file` добавляет те же файлы, что и у `serve`. К API команды не обращаются, токен не нужен.

- `tools list` печатает таблицу: имя, уровень доступа, операция, фиксированные аргументы, есть ли фильтр `jq`, файл. Инструменты выше уровня доступа сервера при запуске не регистрируются.
- `tools check` проверяет файлы так же, как `serve` при запуске (TOML, поля, операции, фиксированные аргументы по схеме операции, фильтры `jq`, совпадения имён), и печатает для каждого файла `OK` и число инструментов. Ошибка — код выхода не 0 и сообщение с файлом и инструментом.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `TRACKER_MCP_CONFIG_DIR` | Каталог с `profiles.toml` и `tools.toml` вместо `~/.config/tracker-mcp`. |
| `CODEX_HOME` | Каталог конфигурации Codex для `connect codex` вместо `~/.codex`. |
| `RUST_LOG` | Уровень логов `serve` в stderr, если не задан `--log-level`. |

Токен Tracker из переменных окружения не читается никогда.
