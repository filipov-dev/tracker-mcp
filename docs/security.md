# Безопасность

Сервер даёт агенту доступ к Tracker от имени пользователя токена. Ниже — какие границы держит сам сервер и что остаётся на стороне пользователя.

## Токен

- Токен выдаёт ваше собственное OAuth-приложение Яндекса: своего приложения в `tracker-mcp` нет. Права токена задаются правами приложения: агенту, которому достаточно чтения, давайте токен приложения только с `tracker:read` ([OAuth-приложение](oauth.md)).
- Токен хранится только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Запись: сервис `dev.filipov.tracker-mcp`, учётная запись — имя профиля.
- Токен вводится только скрытым вводом (`connect`, `auth login`) или через stdin (`auth login --token-stdin`). Он не принимается аргументом командной строки и не читается из переменных окружения или `.env`.
- Ни одна команда не печатает токен: `auth status` и `serve --status` показывают только, сохранён ли он.
- В конфигурацию MCP-клиента попадает только команда `tracker-mcp serve --profile <профиль> …`, в `profiles.toml` — настройки профиля без токена.
- Токена нет в аргументах инструментов. Заголовки `Authorization`, `X-Org-ID` и `X-Cloud-Org-ID` добавляет сервер, и `api_request` не может их переопределить.
- Токен уходит только в Tracker API (`https://api.tracker.yandex.net`) и вырезается из любого текста, который получает агент.
- Один клиент — один профиль — одно OAuth-приложение и токен. Тогда токен любого агента можно отозвать, не затрагивая остальных.

Всё это относится к stdio-серверу. В [HTTP-режиме](http.md#токен-и-организация) хранилища нет: токен приходит в заголовке каждого запроса, лежит в конфигурации MCP-клиента и виден агенту. Сервер его не сохраняет и не пишет в логи, но граница безопасности там — права токена, а флаги доступа сервера — страховка от ошибок агента ([модель угроз](http.md#модель-угроз)).

## Уровни доступа

По умолчанию сервер работает только на чтение. Запись (`--allow-write`) и удаление (`--allow-destructive`) включает пользователь при запуске сервера или в `connect`. Инструменты выше разрешённого уровня не регистрируются, а `api_request` не отправляет запросы выше этого уровня ([MCP-инструменты](tools.md#уровни-доступа)).

Уровень доступа сервера не заменяет права токена: Tracker проверяет права пользователя и приложения. Сервер только сужает то, что агент может сделать с этим токеном. Но токен с правом записи остаётся токеном с правом записи: если он утечёт (например, агент с доступом к оболочке прочитает его из хранилища или пользователь вставит его не туда), им можно писать в обход сервера. Поэтому агенту только на чтение нужен токен приложения только с `tracker:read`.

## Учётные данные в ответах

Агенту не нужны пароли и токены внешних сервисов, а из его контекста они легко попадают в логи, коммиты и документацию. Поэтому сервер заменяет на `[redacted]`:

- строковые значения полей, имя которых похоже на учётные данные, на любой глубине: `password`, `passwd`, `pwd`, `passphrase`, `secret`, `token`, `access_token`, `refresh_token`, `private_key`, `api_key`, `client_secret`, `credentials`, `authorization`, `cookie`, в том числе с префиксом (`db_password`, `X-Api-Key`, `X-Auth-Token`, `Set-Cookie`) и в camelCase (`accessToken`);
- все значения в объекте способа авторизации `authContext` (`webhookAuthContext`), кроме описательных: `type`, `login`, имя заголовка;
- значения заголовков в объектах `headers` настроек и журналов триггеров, автодействий, макросов и вебхуков, кроме заведомо безопасных (`Content-Type`, `Content-Length`, `Date`, `Server` и подобных): у заголовка с ключом может быть любое имя;
- значения, похожие на секрет по форме, в любом тексте, включая описания задач и комментарии: OAuth-токены Яндекса (`y0_…`, `AQAAAA…`), IAM-токены (`t1.…`), JWT, значения после `OAuth`, `Bearer` и `Basic`, блоки закрытых ключей PEM, пароль в URL (`https://user:пароль@host`). Заменяется только сам секрет, текст вокруг остаётся.

Не скрываются идентификаторы постраничной выдачи (`scrollId`, `scrollToken`, `pageToken`, заголовки `X-Scroll-Id` и `X-Scroll-Token` в `pagination`), признаки вида `has_password` и `isSecret`, пустые строки и поле `headers` вне интеграций (например, заголовки таблиц виджетов). Те же правила действуют для ответов `api_request` и для текстов ошибок Tracker. Токен самого сервера дополнительно вырезается из любого текста, который уходит агенту.

В инструкциях сервера агенту сказано не просить токены и пароли в чате, не пытаться восстановить скрытые значения и не переносить персональные данные из ответов (имена, логины, почту, тексты задач и комментариев) в логи, коммиты, код, тестовые данные и Wiki без явной просьбы пользователя. Если Tracker отклоняет токен (HTTP 401), агент предлагает пользователю выполнить `tracker-mcp auth login --profile <профиль>` с профилем, на котором запущен сервер.

## Локальные файлы

Загрузка файлов (аргумент `file`, например у `post_attachment`) и скачивание (аргумент `save_to` у инструментов, которые возвращают файл, например `issues_get_attachment`, и у `api_request` для таких операций) работают только с путями внутри разрешённых каталогов:

- рабочий каталог сервера, если это не корень файловой системы и не домашний каталог;
- системный временный каталог: он разрешён для черновых файлов и скачивания во временные файлы, но общий для всех программ пользователя, поэтому не держите в нём ничего личного;
- каталоги из `--allow-path`.

Пути проверяются после раскрытия `..` и символических ссылок: файл или каталог, который ссылкой ведёт за пределы разрешённых каталогов, отклоняется и при загрузке, и при скачивании (в том числе каталог назначения `save_to`). Относительный путь считается от рабочего каталога сервера. `save_to` указывает на новый файл: существующие файлы и символические ссылки не перезаписываются. Файл открывается по проверенному пути, после открытия сервер сверяет, что путь не подменили (например, заменой каталога на ссылку между проверкой и открытием); при подмене файл не отправляется и ответ в него не записывается.

## Протокол и логи

- stdout занят протоколом MCP; логи и диагностика пишутся только в stderr. Уровень — `--log-level`, иначе `RUST_LOG`, иначе `warn`. Токен и заголовки организации в логи не попадают.
- Ошибки Tracker (`4xx`, `5xx`) и запрещённые вызовы возвращаются агенту как результат инструмента с `isError: true`; процесс не падает.
- stdio-сервер не открывает сетевых портов и ходит только в Tracker API. Редиректы на другие хосты не выполняются.
- HTTP-сервер (`serve --http`) по умолчанию слушает только `127.0.0.1`, проверяет `Host` и `Origin` (защита от DNS rebinding) и без токена отвечает `401`. Снаружи loopback его нужно закрывать TLS ([HTTP-режим](http.md#за-reverse-proxy-с-tls)).
